## October 14: have the current-price tool supply Eastern display times

The daily "evening toll" check (Route 7 to I-495 South, westbound I-66) kept
failing on the time. The tool already converted every timestamp to New York time,
with daylight saving applied. But it sent ISO text such as
`2026-10-13T17:12:27-04:00`, and the agent sometimes treated the `-04:00` as
"subtract four hours". Between October 8 and 13, 3 production runs reported an
observed toll. Two of them gave the observation time as **1:12 PM EDT instead of
5:12 PM EDT**, and the judges failed them. The prompt already said not to subtract
the offset, and the error still happened.

Current-price tool contract **1.6.0** adds ready-to-show strings next to the
unchanged ISO fields: `observed_time` (`5:12 PM EDT`) and `evaluated_time`
(`10/13/2026 5:24 PM EDT`). The EDT/EST label comes from the New York time zone
rules, so the switch to EST on November 1 needs no prompt or code change. A
validator rejects any display string that doesn't match its timestamp. System
prompt **2.3.17** tells the agent to copy these strings exactly. The deterministic
daily check keeps its own independent time formatting.

Fixtures and references in all three splits received the same derived strings.
The splits were refrozen as corpus **5.2.13**, skipping 5.2.3-5.2.12 because
external holdout copies from the open resolver work already use those numbers.
No case wording, route or price changed. Claude recorded input approval at
Ryan's request; no one inspected the cases. Approval of the harness 2.5.19
calibration still applies because no evaluator source changed.

| Training | **50/50** valid | $0.075641 |
| Shadow | **10/10** valid | $0.014400 |

The one invalid holdout exchange was not inspected. The October 10 holdout run

## October 14: remove the holdout guard hook

At Ryan's request, the Claude Code hook that blocked agent tool calls naming the
external holdout was removed. Holdout runs already required him to disable it
by hand, and it also blocked harmless commands. Holdout separation is
now procedural only: the agent may run the migration, freeze and aggregate
commands, but does not read case content or detailed evidence. Earlier holdout
results are unaffected.

## October 15: compare the v1.2.0 candidate with the production agent on holdout

Before the v1.2.0 release, Ryan asked for holdout numbers on the release
scorecard that let a reader compare the candidate with the agent it replaces.
The production agent (v1.1.2: system prompt 2.3.15, current-price tool 1.5.1)
had October 10 holdout runs that never reached the scorecard. The candidate
(`532f9fed`: prompt 2.3.17, tool 1.6.0) had no pass³ score at all.

Both agents ran on one day under harness 2.5.19 and its approved calibration:
five alternating holdout runs each and one training run each, three trials per
case. The production agent cannot read tool 1.6.0's new time fields, so it ran
corpus 5.2.2. That corpus has the same cases, routes and prices as 5.2.13, without
the derived display strings. Its prompt, agent and tool code matched v1.1.2 byte
for byte, except a version label. Only aggregate holdout output was read.

| Agent | Holdout pass³ by run | Mean | Holdout trials passed (of 375) | Inconclusive | Training pass³ (1 run) |
| --- | --- | ---: | ---: | ---: | ---: |
| v1.1.2 production (2.3.15) | 72, 76, 76, 64, 72 | **72.0%** | 316 | 4 | 78% (39/50) |
| v1.2.0 candidate (2.3.17) | 72, 72, 88, 72, 88 | **78.4%** | 324 | 1 | 82% (41/50) |

The candidate's mean holdout pass³ is 6.4 points higher and its trial pass rate
2.1 points higher. The run ranges overlap (64-76 and 72-88), so the gain is about
the size of the run-to-run spread: an observed improvement, not a confirmed one.
Training minus holdout pass³ was +6.0 points for the production agent and +3.6
for the candidate, each from a single training run. The holdout is still not
blind: it was read on October 10, and aggregate holdout checks informed the 2.3.16
choice. The measurement covers both agent changes together.

Spend was **$4.77** with complete usage: $3.48 for holdout and $1.29 for training,
against a $7 cap.

Decision: **publish both agents' results on the release scorecard and release
v1.2.0.**

## October 16: move production billing refreshes off the hour

On October 9, development's billing refreshes at 08:00 and 12:00 UTC both failed
with OpenAI rate-limit errors, so development moved to 08:17 and 12:17 UTC (see
[October 9](2026-10-05.md#october-9-prepare-an-off-hour-development-billing-schedule)). All **13** scheduled development refreshes from
October 10 to 16 then published, with no OpenAI failures or retries.

Production stayed at 09:00 and 13:00 UTC. Its 09:00 refresh on October 16 got
HTTP 429 `rate_limit_exceeded` from OpenAI's costs endpoint on all three attempts
within eight seconds. The dashboard kept its October 15 publication and the
failure alarm fired. Development had succeeded 43 minutes earlier running the
same publisher code. This matches Ryan's observation that on-the-hour runs get
429s. Limitations: most earlier 09:00 production refreshes succeeded, the sample is
small, and OpenAI's response gave no reason.

Decision: **move production to 09:17 and 13:17 UTC**, still twice daily and an
hour after development's AWS feed. Publisher code and retries are unchanged.
