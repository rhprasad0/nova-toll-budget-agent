It plans the calls. It doesn’t price the trip.

The new routing tool turns two exact road locations into the only oracle-supported sequence of pricing-tool calls and untolled handoffs. Think of it as air traffic control for four specialists.

The one-sentence mental model

A small directed graph sits above the corridor tools, stops them at verified interchange boundaries, and refuses any journey the committed evidence cannot connect.

01 · Core idea

One route, four responsibilities.

The agent resolves human language first. The planner then proves a route exists. Only after that may the specialized tools fetch or calculate prices.

1

Resolve exact labels

The agent maps “Dumfries” or “Tysons” to a priced corridor and an exact oracle label.

2

Validate direction

The origin must be entry-capable and the destination exit-capable. Similar names are not interchangeable.

3

Search proven edges

Breadth-first search considers only direct oracle pairs and the eight committed one-way handoffs.

4

Return a call plan

Priced legs name the allowed tool. Connector steps describe a $0 boundary and are never priced.

02 · The graph

A deliberately small road network.

Corridors contain hundreds of valid origin–destination pairs. The planner treats those dense internal maps as a simple “can this tool price this leg?” check, then searches a tiny handoff graph between them.

04 · Guardrails

The refusal is a feature.

The planner is conservative by design. Missing evidence produces an error, not an imaginative detour or a suspiciously convenient fare.

↔

Direction selects the boundary

VDOT lane status selects Edsall southbound or Franconia-Springfield northbound; I‑495 pricing resumes at Braddock node 191NO.

×

No unsupported edge

If neither a direct oracle pair nor a committed transfer reaches the destination, the result is an explicit “no supported directed route” error.

$

No invented price

The junction is unpriced, never $0. Known segment fares remain separate and never become a complete trip total.

Under the hood: the entire search strategy

The frontier begins with the exact origin. For each state, the planner first checks whether the destination is directly priceable. If not, it tries every outgoing transfer whose source is reachable from the current point. A visited set prevents cycles; breadth-first order returns the first supported sequence.

frontier = [(origin_corridor, origin)]
visited = {origin}

while frontier:
    state = frontier.pop(0)
    if destination_is_directly_priceable(state):
        return priced_step

    for transfer in NETWORK_TRANSFERS:
        if transfer_source_is_priceable(state):
            frontier.append(
                priced_leg
                + zero_dollar_connector
                + transfer_target
            )

return "no oracle-supported directed route"
